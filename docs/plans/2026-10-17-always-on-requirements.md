# atelier 为常驻智能体需要补的能力（需求清单）

> 来源：`/home/ystyle/Projects/Cangjie/docs/plans/2026-10-02-always-on-agent.md`（总设计 **v4**）。
> 本文把总设计里**归属 atelier（内核）**的部分抽出来，整理成可开工的需求清单。
> 只列 atelier 侧要做的；世界树 / starline / 记忆层的项见总设计 §2.2 的缺口表。
>
> 一句话：**现有 run 假定用户在场。常驻 agent 大部分时间不在 run 里，也没有人守着。**
> atelier 要补的正是这两件事——run 之外的语义，与无人在场时的语义。
>
> **v2 修订（2026-10-17，对齐总设计 v4）**，三处**结论性变化**：
> 1. **新增 A 组的第 0 步**：总设计 v4 的 §6.0 **首次定义了 run**（三层模型）。
>    在这之前本文把 run 当既有概念用，**"要不要补 run"这个前提本身没被审过**。
>    现在明确了：**run 保留，但入口要从"会话绑定"改成"注意力快照绑定"**——
>    这是**所有其它项的前置**（原文档缺这一步）。
> 2. **A2 预授权大幅降级**：部署形态定为 **agent 独占一个 Linux 用户**（总设计 v4 §6.6），
>    隔离边界下沉到操作系统。**应用层授权体系（凭证代理 / Sentinel / 授权范围分级）不做**，
>    预授权从"安全边界"降级为"**便利性开关**"。**能力量级完全不同了。**
> 3. **新增 E 组（进程与隔离的 atelier 侧）**：隔离有 atelier 要配合的部分
>    （挂起等人 → 代执行的特权通道、资源上限的可观测、审计埋点），原文档完全没有。

## 0. 结论摘要

要补的能力分五组。**A0 + C 是真正的前置**，A/B 是阻塞项：

| 组 | 能力 | 性质 | 阻塞 | 对应总设计 |
|---|---|---|---|---|
| **A** | **run 语义**：A0 **入口解绑会话**（前置）· A1 RunPolicy · A2 便利性预授权 · A3 门控接口 | 内核级语义 | ✅ 是 | §6.0 · §6.1–§6.2 · §6.4 |
| **B** | **run 之外的状态流**（空闲/等待/挂起/排队） | 内核级语义 | ✅ 是（面板刚需） | §6.5 |
| **C** | **触发源是一等公民**（谁触发了这次 run） | 接口扩展 | ✅ 是（决定用哪套策略） | §6.3 |
| **D** | **成本与执行侧约束**（缓存友好布局 · PTC 注册 · 压缩边界 · 持久执行） | 约束 + 新功能 | 部分 | §8.3 · §5.9 · §5.10 · §7 |
| **E** | **隔离的 atelier 侧配合**（特权代执行通道 · 资源自限 · 审计埋点） | 接口 + 纪律 | ⚠️ 上线门槛 | §6.6 |

**可开工顺序**：

```
A0（入口解绑）──┬─→ C（触发源）─→ A1（RunPolicy）
                │                      ↓
                └─→ B（间隙状态）←─────┘
                                        ↓
                              A2（便利性预授权）
D1（约束，随时遵守）· D2/D3（可后置）· D4（可后置）
E（上线前必须完成，可与上面并行）
```

**A0 是新增的关键前置**：不先解绑会话，A1 的 RunPolicy 无处安放——因为
`chatWithSessionId` 的签名里根本没有"这次 run 用什么策略"的位置。

## A. run 语义

### A0. 入口解绑会话（**v2 新增，一切的前置**）

**问题**：总设计 v4 §6.0 明确了 run 的定位（Runtime 内的一次执行），并指出 atelier
现状与它的差距。**这是本文档原版缺失的一步**——原版直接从"RunPolicy"开始，
但 RunPolicy 需要一个能承载它的 run 入口。

**现状（已核实）**：

| 位置 | 现状 | 为什么不满足 |
|---|---|---|
| `atelier/src/agent/runtime.cj:562` | `chatWithSessionId(sessionId, messages, env)` | **会话挂靠焊在入口上**：调用方必须给 sessionId，panel 模式（无会话）用不了 |
| `atelier/src/agent/session_loop.cj:43` | `SessionLoop.run(sessionId, inputText, ...)` | 面向"历史 + 输入文本"，同样把会话当前提 |
| `atelier/src/context/system_prompt_builder.cj:12` | `PromptSegmentContributor`（**目前无宿主使用**） | **现成的接缝**：宿主往系统提示注入自定义段。面板渲染从这里进系统提示，是把 starline 接上 run 的最小改动 |

**要补的**：

- 一个**不落会话树、以消息数组为输入**的 run 入口（供 panel 模式用）；
- 该入口要能表达**注意力快照**而非"整段会话历史"（面板渲染 + 最近 N 条 + 记忆概览）；
- **保留** `chatWithSessionId` 给会话型宿主（acp / a2a / server / 子代理都在用，不能动）；
- 面板渲染的注入走 `PromptSegmentContributor`，**不要**另造一套上下文拼装。

**验收**：能跑一个"无 sessionId"的 run，其系统提示里带面板渲染，事件流与工具执行
与现有一致（`AgentEvent` 全套、`cancelSession` 等效能力、工具预算生效）。

### A1. RunPolicy：给 run 补一种运行模式

| 情形 | 交互式（现状） | **无人值守（新增）** |
|---|---|---|
| **提问** | 等用户答复 | ① 按预授权回答；② **挂起为 pending** 等用户回来；③ 拒绝并记录 |
| **审批** | 发审批请求 | **见 A2 的 v2 降级说明** |
| **失败** | 报错给用户 | ① 重试（含**退避**）；② 放弃并记录；③ 转人工 |

**要求**：

- 模式是 run 的一个属性（`attended` / `unattended`），**由触发源决定**（见 C）；
- 三种情形都要**落日志**（做了什么决定 + 理由 + 置信度），否则事后无法回答
  "昨天那件事它为什么没理我"；
- 「挂起」必须是**可恢复的终态**，不是进程内的等待——要与 D4（持久执行）对齐。

> ⚠️ **v2 关键修订**：上表「审批」一行原为「**预授权策略**（这类操作不用问）」。
> 在总设计 v4 §6.6 的部署形态下（agent 独占 Linux 用户），**审批的语义变了**：
> 隔离由 OS 承担，**不再需要应用层判断"这次操作该不该允许"**——agent 在自己用户下
> 能做的事就是被允许的事。**因此 A1 的重心从"审批策略"移到"提问挂起 + 失败策略"。**

### A2. 预授权策略（**v2 降级：从安全边界 → 便利性开关**）

**原设计**（v1）想做的是「表达哪一类操作不必问」，并追问它与 `allow_always` 的
主从关系、硬规则只能更严、服务不可用一律按"要问"处理。**v2 保留这些纪律，但量级下降了**：

| 原 v1 要求 | v2 处置 | 理由 |
|---|---|---|
| 预授权的**声明与持久化**（按工具名/参数模式/风险级别） | ⚠️ **降级为便利性配置**，不做安全论证 | 隔离边界在 OS，不在这里 |
| 与 `allow_always` 的**主从关系**（避免两个真相） | ✅ **仍必须定** | 这是实现层面的坑，与安全等级无关 |
| 硬规则只能让判决更严 | ✅ **保留**（低成本，防手滑） | 沿袭 `jev-style` guard 的设计 |
| 服务不可用/超时 → 一律按"要问"处理，绝不静默 allow | ✅ **保留**（成本几乎为零） | 同上 |

**已有基础（已核实，不变）**：

| 已有 | 位置 | 说明 |
|---|---|---|
| `TrustDecision { Allowed / NeedsApproval / Denied }` | `atelier/src/trust/gate.cj` | 三档判决已定义 |
| `TrustState { Undecided / … }` | `atelier/src/trust/manager.cj` | 未决定 → `NeedsApproval` |
| 审批选项 `allow_once` / `allow_always` | `atelier/src/interaction/user_request.cj:151-152` | **包含「本目录下不再询问」**——预授权的形状已在 |
| `UserAnswerStatus.Pending` | 同上 `:178` | 「宿主决定挂起：runtime 据此结束本次 run」 |

**所以缺的不是"预授权"这个概念，而是它的自动化语义**：`allow_always` 目前要**用户点一次**
才生效；无人值守时**没有人点**。

> ⚠️ **仍然存在的真实风险（不要因为降级就忽略）**：OS 用户隔离**挡不住同一 uid 内的破坏**。
> `rm -rf`、`docker` 组、写自己的配置——这些 agent 都有权限。所以**高危动作的防护
> 从"内核机制"退化为"产品规则"**（写进提示词 / 技能 / 工具声明），**不再有强制力**。
> 这是总设计 §6.6.2 标注的代价，atelier 侧只能通过**日志留痕**（见 E3）补偿。

### A3. 与决策模型的分工（唤醒门控的落点）

总设计 §6.4 定了 **规则 → Jev → lead** 的分级判定。**atelier 侧要提供的是接口，不是模型**：

- 接口固定为 `decide(概览特征) -> Decision`（`Decision` = 判定 + reason + 置信度），
  **换实现不动上层**；
- **输入必须是概览层**（日/小时总结 + 变化统计特征），**不看原文**——喂原始数据
  等于把省下的钱还回去；
- **职责不许越界**：门控只回答「**要不要**唤醒」，**不回答「该做什么」**（那是 lead 的事）。
  职责一模糊就会演变成"顺手也让 Jev 把事办了"；
- **误判代价不对称**：漏报（该醒没醒）比误报（白醒一次）伤得多 → 阈值**偏保守**，
  宁可多醒几次，也不能让它变成哑巴。

> **Jev 的选型已调研**（总设计 §6.4）：官方实现 `jev-style`（Apache-2.0，自带 MCP server
> 与 `decide`/`noul`/`choice`/`score` 工具）。**仍待定的是接入路径**——走它的 MCP，
> 还是在仓颉侧直连 `jev-style serve` 的 HTTP API。详见忆时塔 `cangjie-mem` 的记忆 `jev-style`。

## B. run 之外的状态流 ⭐ 容易被忽略

### B0. 问题

`AgentEvent`（**14 种**）是 **run 内**的事件流。而常驻 agent **大部分时间不在 run 里**：
它在**空闲、等触发、等审批、排队**。

而 starline 的核心价值是「人和 LLM 看同一块屏」——屏幕上必须能显示**等待中的它**，
否则只能显示"上一次干了什么"。**这一条不补，产品形态就立不起来。**

> **已有基础（比想象中好）**：`SuspendEvent` 已经在 `AgentEvent` 里，语义写得很准——
> 「本次运行挂起：等待外部结果（前端执行工具、用户确认……）。**挂起不是失败**：
> 历史停在 `assistant(tool_calls)`，调用方带结果发起下一次 run 即可继续。」
> 也就是说**「挂起」这个动作在 run 内已经表达出来了**。
> 缺的是**run 结束之后**那段时间的状态——谁在等、等什么、等多久。

### B1. 要补的状态

| 状态 | 含义 | 面板要显示什么 |
|---|---|---|
| `idle` | 空闲，等触发 | 在等什么（哪些触发源在监听） |
| `pending-input` | 挂起，等用户回答 | 问的是什么（可回答入口） |
| `pending-approval` | 挂起，等用户审批 | 审批什么（可批准/拒绝入口） |
| `pending-privileged` | **挂起，等系统用户侧代为执行特权操作**（v2 新增，见 E1） | 请求了什么特权、等谁批 |
| `queued` | 已触发、在排队 | 排在谁后面、为什么 |
| `running` | 正在 run | 现有 `AgentEvent` 已覆盖 |
| `failed-deferred` | 失败后按策略延后重试 | 下次什么时候、失败了几次 |

**要求**：这些状态要**与 run 内的 `AgentEvent` 同一套流**（同一订阅面、同一持久化），
否则面板要订阅两套东西、且两套之间会有竞态。

### B2. 与 A1 的关系

A1 的「挂起为 pending」**必须**在这里可见——挂起不可见 = 用户不知道它在等自己，
**功能上等于卡死**。E1 的「特权代执行」同理。

## C. 触发源是一等公民

### C0. 问题

`run` 现在**由用户输入驱动**（且绑在 `sessionId` 上，见 A0）。需要能表达**这次是谁触发的**——
用户 / 渠道消息 / 定时器 / 外部事件 / 远端 A2A。

**它不是元数据，它同时决定三件事**：

| 决定 | 说明 |
|---|---|
| **用哪套策略** | 无人值守 or 交互式（A1） |
| **怎么记账** | 成本归到谁头上（外部触发可能高频，见总设计 §6.4 的"高频小额更容易失控"） |
| **结果投递给谁** | 回原渠道 / 只上面板 / 不投递 |

> **v2 补充（来自总设计 §12.1 的外部依据）**：业界明确把这两件事拆开——
> **「触发机制决定什么时候创建一次新的执行；授权机制决定这次执行里允许做什么」**，
> 且「一个事件只负责创建一次执行，**不会自动增加这次执行的权限**」。
> 本文 v1 把两者写在一句话里（"它同时决定三件事"含授权语义），**v2 明确：触发源不决定权限**，
> 权限由 OS 用户（E 组）决定。

### C1. 要补的接口

- `run` 签名带上**触发源**（类型 + 标识 + 可选元数据），且**落进会话日志**（可回溯）；
- 触发源应作为**可扩展类型**，而不是枚举——渠道体系是插件，
  世界树会不断加新渠道（总设计 §4.1）。

## D. 成本与执行侧

### D1. 缓存友好的提示布局（**约束而非功能**）

**缓存命中与未命中差 50 倍**，是整个成本模型里最大的杠杆（总设计 §8.3）。

**要求**：系统提示 / 工具定义保持**稳定前缀**；**动态内容一律后置**
（时间戳、随机顺序的工具列表、按次变化的记忆概览）。

> 注意：体积最大的部分（系统提示 3–5K + 工具定义 5–15K）恰好每次相同 → 几乎全在缓存里。
> 这个约束不需要新功能，但**要在写提示构造代码时就遵守**，事后改成本很高。
>
> **与 A0 的关联**：A0 要把面板渲染注入系统提示（`PromptSegmentContributor`），
> 而面板内容**每次都变**——**这份注入必须放在动态段（前缀之后）**，否则会把
> 缓存命中率打掉、单价 ×50。**A0 与 D1 必须一起设计，不能分先后。**

### D2. 记忆/面板只读接口的 PTC 化

分层记忆给**结构**，但"按结构取数"若逐轮 function call，中间结果仍会灌进上下文。
`atelier/src/ptc/` 已具备 `PtcBindings` / `XispRuntime` / `JsonBridge` /
`BuiltinFunctions.registerPure`（**纯函数子集 = 安全边界**）。

**缺的是**：把**记忆与面板的只读检索接口注册成纯函数**，并给出一份
**准确且短**的 SDK 说明（`PtcSdkRenderer` 具备此能力）。

> **判据（重要）**：PTC 省的是**中间结果**，不省**程序本身**。
> ✅ 适合：多步 + 大中间结果 + 只读（记忆检索、面板数据读取、日志扫描、指标聚合）；
> ❌ 不适合：有副作用的动作（绕过人在环）、需要逐步判断的探索、单次简单调用。
> **SDK 写得含糊会导致模型反复试错，把省下的 token 又花回去。**

### D3. 记忆层与上下文压缩的边界（**纪律，不是功能**）

两者触发条件不同，混成一根管子之后，调窗口参数会莫名改动记忆质量：

| | 上下文压缩（已有） | 记忆层沉淀 |
|---|---|---|
| 目的 | 塞进上下文窗口 | 将来能检索回来 |
| 触发 | **token 用量**驱动 | **分段信号**驱动 |
| 可丢 | 细节可丢 | 要保留要点 |
| 落点 | 会话内的压缩条目 | 记忆层的总结条目 |

**待定**：同一份摘要是否允许两用（总设计 §11 待决 5）。

### D4. 持久执行（加固项，可后置）

参考 Pi 的 durable harness 模型，崩溃续跑。**与 A1 的「挂起」强相关**：
挂起必须是可恢复的终态。总设计列为 P6，可在 A/B/C 之后做。

## E. 隔离的 atelier 侧配合（**v2 新增**）

总设计 v4 §6.6 把隔离边界放到操作系统：**agent 独占一个 Linux 用户，系统本体跑在另一个用户下**。
大部分工作在世界树/部署侧，但**有三件事必须 atelier 配合**：

### E1. 特权代执行的通道（与 A1 的挂起语义复用）

**场景**：agent 需要装包、改系统配置等特权操作，但**不给它 `sudo`**（总设计 §6.6.3 第 3 条）。
做法是「**请求 → 系统用户侧确认 → 代为执行**」。

**atelier 侧要补的**：

- 一个**新的挂起原因**（与审批、提问并列）：`pending-privileged`（见 B1 表）；
- 载体复用现成结构：`ExternalRequest`（`atelier/src/tool/interface.cj:144`）已能表达"等外部结果"，
  `UserRequest` / `UserAnswer` 的编解码也齐——**新增一种 `reason` 而不是新建一套**；
  > 已核实：`ExternalRequest.reason` 是 **`String` 而非枚举**（现有取值 `tool_call` /
  > `input_required`），所以"加一种 kind"**不需要改类型定义**，只要新增一个取值并在
  > 消费端（AG-UI 翻译器 / HTTP handler / ACP 桥）各加一条分支。成本比预期低。
- 结果回来后按"带结果续跑"处理（`SuspendEvent` 的既有语义，**不需要协程挂起**）。

> **这是 E 组里唯一真正需要 atelier 写代码的项**，且它**复用**了 A1 的挂起机制——
> 做 A1 时顺带把 kind 留出来，成本很低。

### E2. 资源自限的可观测（**纪律**）

无人看管的 agent 可能跑飞，总设计建议用 systemd 的 `MemoryMax` / `CPUQuota` / `TasksMax`
把它关在 cgroup 里。**atelier 侧不用实现限额**，但要：

- **让限额可观测**：agent 侧（`SystemStatus` 类面板的数据源）能读到自己的 cgroup 用量，
  否则"被限额打死的 run"与"业务失败"无法区分；
- **明确被杀死后的语义**：run 被 OOM killer 干掉 → 下次启动时历史停在什么状态？
  这与 D4（持久执行）是同一个问题的两面。

### E3. 审计埋点（**纪律**）

总设计建议「`auditd`（OS 层：动了什么）+ 应用层结构化日志（为什么动）」两路并存。
**atelier 侧负责的正是后者**：

- A1 说的"三种情形都要落日志"、A2 的"预授权决定要可审计"、B1 的状态流——
  **三者应该收敛成同一条结构化日志**，而不是三个地方各打各的；
- **理由**：OS 层只能看到"agent 读了哪些文件、起了哪些进程"，看不到"它为什么这么做"。
  **只有应用层能回答后者**，而常驻 agent 事后追责**必然要回答后者**。

> **E3 是 A2 降级后的补偿**：既然高危动作不再有内核强制力，
> **至少要有可靠的事后追溯**。这条不能省。
